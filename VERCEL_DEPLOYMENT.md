# Deploying PRAMANAM to Vercel

This repo ships with two deployment targets. **Render** (`render.yaml`) runs the
classic two-process topology (web + BullMQ worker). **Vercel** is serverless:
there is no long-running worker process, so the nightly expiry ladder runs
through **Vercel Cron** instead (already wired — see below).

## Architecture on Vercel

| Piece | On Vercel | Notes |
|---|---|---|
| Next.js web app | ✅ Native | App Router, `npm run build` / `next start` — zero config |
| PostgreSQL | ⚠️ External | Use [Neon](https://neon.tech) (serverless Postgres) or Supabase |
| Redis | ⚠️ External | Use [Upstash](https://upstash.com) (serverless Redis, `rediss://` URL) |
| S3 storage | ⚠️ External | MinIO **cannot** run on Vercel — use Cloudflare R2, Backblaze B2, AWS S3, or a hosted MinIO (Render/Railway) |
| BullMQ worker | 🔁 Replaced | `vercel.json` cron → `GET /api/v1/cron/expiry-scan` (Bearer `CRON_SECRET`) at 19:00 UTC = 00:30 IST |
| Cert signing (Ed25519) | ✅ Works | Keys via env vars, `node:crypto` in the Node runtime |
| Boot gate (`lib/security/env.ts`) | ⚠️ Active | Production refuses to boot without real secrets — fill every env var below |

## Environment variables (Vercel → Project → Settings → Environment Variables)

| Key | Example / how to get it | Notes |
|---|---|---|
| `DATABASE_URL` | Neon pooled connection string | Use the **pooled** URL (host ends `-pooler…` / `?pgbouncer=true`) — Prisma + serverless |
| `REDIS_URL` | `rediss://default:…@…upstash.io:6379` | Upstash REST is NOT used — copy the standard Redis URL |
| `JWT_SECRET` | `openssl rand -hex 32` | ≥32 chars, never demo values (boot gate rejects them) |
| `JWT_REFRESH_SECRET` | `openssl rand -hex 32` | Must differ from `JWT_SECRET` |
| `ED25519_PRIVATE_KEY` | base64 PKCS8 | Generate: `openssl genpkey -algorithm ed25519 \| base64 -w0` |
| `ED25519_PUBLIC_KEY` | base64 SPKI | `openssl pkey -in key.pem -pubout \| base64 -w0` |
| `ED25519_KID` | `pramanam-2026-08-01` | Optional; travels in JWS header + JWKS |
| `S3_ENDPOINT` | `https://<accountid>.r2.cloudflarestorage.com` | R2/B2/hosted MinIO endpoint |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | from provider | NOT `pramanam` / `pramanam123` (boot gate rejects demo creds) |
| `S3_BUCKET` | `pramanam-docs` | Bucket is auto-created + versioned on first upload |
| `NEXT_PUBLIC_APP_URL` | `https://<your-app>.vercel.app` | Must be **https** in production |
| `PAYMENT_MODE` | `demo` | No real gateway integrated; production requires demo |
| `ALLOW_DEMO_PAYMENT` | `true` | Explicit opt-in for the mock payment path |
| `CRON_SECRET` | `openssl rand -hex 32` | Vercel Cron sends it as `Authorization: Bearer …` |
| `TRUST_PROXY` | `true` | Vercel is a trusted proxy — enables real per-IP rate-limit keys |

> **Keys must be set BEFORE first boot.** `instrumentation.ts` runs
> `assertProductionEnv()` on every production start and throws on demo/missing
> secrets, missing crypto keys, or missing `REDIS_URL`/`DATABASE_URL`.

## Deploy steps

### 1. Provision the backing services
1. **Neon** → create project → copy the **pooled** connection string.
2. **Upstash** → create Redis (same region as Neon) → copy `rediss://` URL.
3. **R2 / B2 / hosted MinIO** → create bucket credentials + endpoint.

### 2. Seed the database (one-time, from your machine)
```bash
# point .env at the production DATABASE_URL first
npm run db:push        # apply prisma/schema.prisma
npm run db:indexes     # pg_trgm GIN + btree indexes (search performance)
npm run db:seed        # idempotent demo seed (no-op when data exists)
```

### 3. Deploy the app
- **GitHub flow:** push this branch to `main` → vercel.com → *Add New Project* →
  import `smarpitm/SIH_2026` → paste the env vars → Deploy. Framework preset
  auto-detects Next.js; no build-command overrides needed (Prisma client is
  generated by the `postinstall` hook).
- **CLI flow:**
  ```bash
  npm i -g vercel
  vercel link
  # add env vars: vercel env add <KEY> production   (or paste in the dashboard)
  vercel --prod
  ```

### 4. Verify
- `GET https://<app>/api/v1/public/stats` → `{ ok: true, … }` (this is also the
  deployment's health endpoint).
- Log in as an ADMIN and hit `POST /api/v1/certificates/expiry/scan` to sanity
  check the same sweep the cron will run.
- Manually test the cron route:
  ```bash
  curl -H "Authorization: Bearer $CRON_SECRET" https://<app>/api/v1/cron/expiry-scan
  # → { ok: true, data: { scanned, flipped, reminders, repaired } }
  ```
- Verify a certificate end-to-end from `/verify/PRM-CERT-2026-00001`.

## Cron details (vercel.json)

```json
{ "crons": [{ "path": "/api/v1/cron/expiry-scan", "schedule": "30 19 * * *" }] }
```

- `30 19 * * *` UTC = **00:30 IST nightly** — the same slot the BullMQ worker
  uses on Render.
- The route runs the expiry ladder **and** the stranded-PASSED repair sweep —
  both idempotent (guarded updates, `dedupeKey` on notifications), so Vercel
  retries are harmless.
- Vercel Hobby allows one scheduled invocation per day — this schedule fits.
- If the sweep ever grows slow with many certificates, raise the function
  timeout in `vercel.json` under `functions` (`maxDuration`).

## Notes & gotchas

- **MinIO demo compose is dev-only.** `docker-compose.yml` is for local
  development; production object storage must be a hosted S3-compatible service.
- **Keep Render as a fallback.** `render.yaml` still deploys the full topology
  (web + worker + MinIO) — the two targets share the same database schema and
  API, so you can run either.
- **Rate limiting** falls back to in-memory only when `REDIS_URL` is unset;
  production always has Upstash configured, so limits are durable.
- **`next.config.mjs`** splits dev/production `distDir` (`.next` / `.next-build`)
  — harmless on Vercel; build and runtime both resolve production to the same
  directory.
